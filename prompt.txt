
# Разработка Django-приложения documents

Заверши разработку Django-приложения `documents` на Django 6 с использованием Django REST Framework.

Основная задача — создать остальные необходимые компоненты приложения документов по аналогии с уже реализованным и работающим приложением `messages`.

## 1. Исходные материалы

Перед началом работы изучи структуру проекта и следующие материалы:

- `documents.sql` — эталонное описание структуры и поведения базы данных для приложения документов.
- `messages.sql` — эталонное описание структуры и поведения базы данных для приложения сообщений.
- `prompt.txt` — приблизительный план организации файлов приложения.
- Существующее приложение `messages` — рабочий пример реализации Django-приложения в этом проекте.

ORM-модели для приложений `messages` и `documents` уже созданы. Повторно генерировать их с нуля не нужно.

**Приложение `messages` уже реализовано и работает.** Изучи его модели, миграции, запросы, административный интерфейс, API и организацию файлов. Используй существующую реализацию как основной пример архитектурного и стилистического оформления.

Основная работа должна выполняться над приложением `documents`.

Файлы `documents.sql` и `messages.sql` не изменять. Они предназначены для сверки структуры, ограничений и бизнес-правил, а не для непосредственного управления схемой базы данных.

## 2. Архитектура проекта

В проекте используется промежуточный подход между стандартной Django-разработкой и использованием специфических возможностей PostgreSQL.

**Django управляет структурой базы данных. PostgreSQL дополняет её механизмами обеспечения целостности данных.**

Не следует воспринимать этот подход как DB-first или PostgreSQL-first архитектуру.

### Django ORM — описание структуры базы

Используй `managed = True`.

Django-модели являются основным описанием структуры управляемых приложением таблиц.

Стандартные миграции Django должны создавать и изменять:

- таблицы;
- столбцы и типы полей;
- первичные ключи;
- внешние ключи и связи;
- индексы;
- ограничения целостности, поддерживаемые Django;
- другие стандартные элементы структуры базы.

Стандартные миграции должны генерироваться на основании ORM-моделей средствами Django: `makemigrations`.

Не создавай таблицы приложения вручную через `CREATE TABLE` в `RunSQL`, если они описаны ORM-моделями и должны управляться Django.

Не дублируй через SQL-миграции индексы, ограничения и связи, которые уже создаются обычными миграциями Django.

### PostgreSQL — дополнительные механизмы целостности

Некоторые правила предметной области и ограничения целостности реализованы средствами PostgreSQL, поскольку они должны выполняться непосредственно на уровне базы данных независимо от способа изменения записей.

Для этого используются триггеры и PostgreSQL-функции.

Они должны устанавливаться отдельными миграциями Django с помощью `RunSQL`.

К ним относятся, например:

- защита неизменяемых записей от изменения и удаления;
- автоматическое обновление временных меток;
- проверка согласованности связанных записей;
- автоматическая синхронизация производных таблиц;
- другие правила целостности, которые должны обеспечиваться непосредственно базой данных.

Триггеры не заменяют стандартные механизмы Django и не должны использоваться для создания таблиц вместо ORM.

### Общие и прикладные PostgreSQL-функции

Разделяй общие и прикладные механизмы.

**Общие функции PostgreSQL** должны находиться в миграциях общего приложения проекта, например `common`, если оно уже предусмотрено структурой.

К ним относятся функции, которые могут использовать несколько приложений: обновление временных меток, защита неизменяемости и общие проверки целостности.

**Прикладные триггеры** должны устанавливаться миграциями соответствующего приложения.

Если триггер вызывает общую функцию, миграция приложения должна иметь зависимость от миграции, создающей эту функцию.

Не создавай копии общих функций для каждого приложения.

Если обнаружатся PostgreSQL-объекты, необходимые для работы ORM, но не создаваемые стандартными средствами Django (например, пользовательские типы ENUM), отдельно проверь их текущую реализацию и порядок создания. Допускаются минимальные специализированные миграции для таких зависимостей, но они не должны переносить управление таблицами из Django в `RunSQL`.

## 3. Сверка ORM-моделей с эталонными SQL-файлами

Перед разработкой остальных компонентов проведи проверку существующих ORM-моделей приложения `documents` относительно `documents.sql`.

Проверь:

- соответствие таблиц и полей;
- физические имена столбцов;
- типы данных;
- схемы PostgreSQL;
- первичные и внешние ключи;
- правила удаления связанных записей;
- значения по умолчанию;
- ограничения целостности;
- индексы и условия частичных индексов;
- пользовательские типы PostgreSQL;
- комментарии таблиц и столбцов;
- соответствие `db_table` фактической структуре;
- корректность использования `managed = True`.

Проверь, что ORM-модели правильно отражают структуру данных, но при этом остаются полноценными Django-моделями, которыми управляют стандартные миграции.

### Правила внесения исправлений

Существующие ORM-модели уже созданы. Их не требуется переписывать заново.

Допускаются точечные исправления, если они необходимы для:

- устранения ошибок модели;
- соответствия эталонному SQL-описанию;
- корректной работы стандартных миграций Django;
- согласованности типов и связей;
- правильной реализации бизнес-логики.

Если обнаружишь расхождения, сначала установи их причину. Не меняй структуру молча и не упрощай модель ради удобства ORM.

Исправления должны быть минимальными и обоснованными.

## 4. Отношение к приложению messages

Приложение `messages` уже реализовано и работает. Оно является примером принятой в проекте архитектуры.

Изучи его, чтобы сохранить единообразие:

- структуру каталогов;
- оформление модулей;
- принципы организации моделей;
- работу с PostgreSQL-триггерами;
- организацию миграций;

Если при сравнении с `messages.sql` обнаружатся ошибки или существенные несоответствия в работающем приложении, допускаются точечные исправления. Они должны быть непосредственно связаны с устранением выявленных проблем.

Не проводи масштабный рефакторинг `messages` ради унификации с `documents`.

Общие компоненты можно вынести или переиспользовать, если это действительно необходимо и не нарушает работу существующего приложения.

## 5. Реализация приложения documents

Изучи `prompt.txt`, существующую структуру приложения `documents` и архитектуру `messages`.

Определи необходимые файлы и создай недостающие компоненты.

Не вводи дополнительные уровни абстракции без практической необходимости.

### Запросы и бизнес-логика

Перенеси существующие витрины данных и запросы в Django-стиль.

Витрины относятся к бизнес-логике приложения. Реализуй их посредством подходящих механизмов Django:

- QuerySet;
- кастомных Manager;
- модулей запросов;
- сервисных функций, если они действительно необходимы.

Сохрани семантику исходных запросов: фильтрацию, сортировку, группировку, агрегацию и связи.

Не создавай SQL VIEW вместо Django-запросов без обоснованной необходимости.

Учитывай производительность запросов. Используй `select_related`, `prefetch_related`, `annotate`, `Subquery` и другие средства ORM там, где это оправдано.

Не переноси в Python операции, которые разумнее выполнить в PostgreSQL.

### Django Admin

Создай административный интерфейс для приложения документов.

Он должен учитывать бизнес-правила и ограничения целостности базы данных.

- Разрешай редактирование только тех данных, изменение которых предусмотрено моделью.
- Не предоставляй административные операции, запрещённые ограничениями PostgreSQL.
- Для неизменяемых записей используй режим просмотра.
- Настрой поиск, фильтрацию, сортировку и отображение связанных объектов.
- Используй понятные русскоязычные названия полей и моделей.

Не пытайся обходить ограничения базы средствами административного интерфейса.

### API — Django REST Framework

Реализуй API приложения `documents` на Django REST Framework.

Предусмотри полноценный CRUD для тех сущностей и операций, для которых он допускается предметной моделью.

Не используй стандартный `ModelViewSet` без анализа особенностей каждой сущности.

Реализуй:

- сериализаторы;
- представления или ViewSet;
- маршруты;
- аутентификацию и разрешения;
- фильтрацию;
- поиск;
- сортировку;
- пагинацию;
- корректную обработку ошибок и ограничений целостности.

Не предоставляй клиенту возможность изменять технические поля, идентификаторы, временные метки и другие поля, значения которых контролируются базой данных.

Способность создавать, изменять и удалять записи должна соответствовать реальным правилам предметной области.

Учитывай работу триггеров PostgreSQL. API не должен обходить или дублировать их логику.

## 6. Миграции

Организуй миграции в соответствии с выбранной архитектурой.

Ожидаемое разделение:

**Обычные миграции Django:**

- создание таблиц;
- изменение полей;
- создание индексов;
- создание ограничений и связей;
- другие изменения структуры, описываемые средствами ORM.

**SQL-миграции через RunSQL:**

- установка прикладных триггеров;
- установка общих PostgreSQL-функций в общем приложении;
- другие необходимые PostgreSQL-механизмы целостности, которые невозможно корректно выразить средствами Django.

Не создавай обычные таблицы приложения через SQL, если они уже описаны ORM-моделями.

Не дублируй операции между обычными миграциями и `RunSQL`.

Проверь порядок и зависимости миграций. Функции должны создаваться до установки триггеров, которые их вызывают. Общие функции должны создаваться в одном месте и переиспользоваться приложениями.

Для SQL-миграций реализуй обратные операции там, где это возможно.

Проверь два сценария:

1. Развёртывание проекта на чистой базе данных.
2. Применение миграций к базе, в которой часть структуры уже существует.

Не используй `--fake` и `--fake-initial` без предварительной проверки схемы и состояния миграций.

## 7. Стиль кода и документации

Сохраняй стиль существующего приложения `messages`.

Язык документации, комментариев и пользовательских названий — русский.

Стиль — нейтральный, технический и лаконичный.

Требования:

- Каждый Python-модуль должен иметь содержательный модульный docstring.
- Классы и функции должны иметь понятные docstring.
- Не используй вводные фразы и прелюдии в документации.
- Комментарии должны пояснять назначение и особенности реализации, а не пересказывать код.
- Используй полные и понятные имена переменных, функций, классов и модулей.
- По возможности избегай сокращений в именах.
- Соблюдай принятые в проекте правила форматирования и организации импортов.
- Не создавай избыточные абстракции.
- Не дублируй код и бизнес-логику.
- Не добавляй зависимости без необходимости.

Применяй лучшие практики Django 6, Python и Django REST Framework с учётом существующей архитектуры проекта.

После завершения работы представь:

9. Проблемы, которые обнаружены, но не удалось устранить.

Главный критерий качества — Django должен управлять структурой базы данных через ORM-модели и стандартные миграции, а PostgreSQL-триггеры должны дополнять эту архитектуру механизмами обеспечения целостности данных.

Сохраняй работоспособность существующего приложения `messages`. Основной результат работы — завершённое, согласованное с ним приложение `documents`.

И ещё один нюанс, который я намеренно оставил в промте: нативные ENUM PostgreSQL. Если твои модели используют `PostgreSQLEnumField`, стандартный Django не создаёт соответствующий тип автоматически. Это нужно проверить отдельно. Вполне возможно, что для него потребуется небольшая предварительная SQL-миграция. Это не означает, что нужно возвращаться к PostgreSQL-first подходу: таблицы по-прежнему должны создаваться и управляться Django.
