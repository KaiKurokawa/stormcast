# Приложение документов

Реализация следует `prompt.txt` и рабочему приложению `messages`.
Эталонный `documents.sql` не изменён; `messages.sql` в предоставленном
дереве отсутствует, поэтому для сообщений использована действующая реализация.

## Созданные и изменённые файлы

- `apps.py`, `__init__.py`: регистрация приложения `stormcast_documents`.
- `fields.py`: переиспользование нативного ENUM-поля из `messages`.
- `hashing.py`: BLAKE3 от канонического JSON RFC 8785 для документов, шаблонов, состояний.
- `querysets.py`: пользовательские лента и карточка вместо SQL-функций витрин.
- `services.py`: транзакционные upsert буфера, фиксация ревизии и запись состояния.
- `serializers.py`: поля входа и выхода, проверка привязок и самоссылок.
- `views.py`, `api.py`: API документов, буферов, ревизий, состояний и шаблонов.
- `admin.py`: добавление и просмотр неизменяемой истории, редактирование и фиксация буферов.
- `models/*.py`: точечные исправления, описанные ниже, и docstring.
- `migrations/0001_types.py`: схема и нативный ENUM.
- `migrations/0002_initial.py`: сгенерированные `makemigrations` таблицы, поля, связи, индексы, CHECK и UNIQUE.
- `migrations/0003_database_triggers.py`, `sql/triggers.sql`, `sql/drop_triggers.sql`: установка и удаление 12 триггеров.
- `migrations/0004_alter_revision_details_and_more.py`: сгенерированные `makemigrations` Python-значения по умолчанию.
- `migrations/0005_database_metadata.py`, `sql/index_comments.sql`: действия удаления существующих FK и комментарии индексов.
- `tests/test_documents.py`: проверки PostgreSQL, API, сервисов, Admin и регрессии messages.
- `common/apps.py`, `common/__init__.py`, `common/migrations/*`: общее приложение и миграция общих функций.
- `configuration/settings.py`, `configuration/api.py`: подключение приложения и маршрутов.
- `docs/superpowers/plans/2026-11-10-documents.md`: план работ.

## Сверка моделей и SQL

Проверены семь таблиц `entities`, `template_entities`, `template_revisions`,
`revision_buffer`, `revisions`, `state_cache`, `states` в схеме `documents`.
Сохранены физические имена полей, UUID идентификаторы документов и шаблонов,
JSONB, BYTEA, временные метки с часовым поясом, строки с ограничениями длины,
нативный ENUM, управляемость `managed=True`, комментарии таблиц и полей.
Сохранены GIN-индексы JSONB с `jsonb_path_ops`, триграммные индексы темы,
частичные индексы состояния и исходящего номера, уникальность личного буфера,
ограничения длины хеша, запрета самоссылок и JSON-массива привязок.

Обоснованные отличия и исправления:

1. `identity.users(UUID)` заменён в исходных моделях на `AUTH_USER_MODEL`.
   Сохранена принятая в messages адаптация к стандартному пользователю Django
   с целочисленным PK. Отчество отсутствует; имя автора строится из фамилии
   и имени, с запасным значением «Неизвестный автор».
2. Убраны `db_constraint=False` у прикладных связей: стандартная миграция
   Django теперь действительно создаёт внешние ключи. Связи пользователей
   также создаёт ORM.
3. Имена CHECK получили префикс `check_documents_`: исходные имена совпадали
   с messages, что блокировало Django check ошибкой models.E032.
   Проверяемые выражения сохранены.
4. Добавлены Python-default для JSON, булевых полей и стадии draft.
   Серверные db_default сохранены. Без Python-default хеширование новых
   объектов получало бы выражения DatabaseDefault вместо значений.
5. К `DocumentEntity` добавлен менеджер пользовательских витрин.
6. Хеш начального состояния в устанавливаемом триггере исправлен на
   `6b4eb78df2fb93cbe5a3034501862580d143d3d3d010055a12c44fba9e910f2b`:
   эталонная константа не соответствует каноническому JSON фактического
   начального состояния с пустыми details. Сам SQL-эталон не редактировался.
7. Проверяющим согласованность состояния триггерам передаётся обязательный
   аргумент `documents.revisions`, отсутствующий в эталонном SQL.

Родитель документа, автор и технические поля не входят в хеш полезной
нагрузки согласно комментариям эталона.

## Миграции и PostgreSQL

Таблицы и индексы создаются только стандартными операциями Django.
Нативный ENUM создаётся до таблиц отдельной RunSQL-миграцией, поскольку
CharField с пользовательским db_type сам не создаёт тип PostgreSQL.
Расширения pg_uuidv7 и pg_trgm уже создаются исторической миграцией messages.

Django задаёт on_delete для ORM-коллектора, но не переносит эти действия
в серверный ON DELETE. Поэтому 0005 корректирует определения уже созданных
FK, сохраняя их имена и количество: CASCADE для entity/template_entity,
SET NULL для parent и RESTRICT для template/revision. Обратная операция
возвращает стандартное NO ACTION. Дополнительные FK не создаются.

Общие функции установлены миграцией common после исторических миграций
messages. Исторические файлы messages оставлены без изменений, чтобы
сохранить применимость к существующим базам. Новое приложение documents
не содержит копий общих функций. Общие функции при откате common
сохраняются, поскольку они уже принадлежат исторической установке messages.

Переиспользуются:

- `common.function_refresh_updated_at_column`;
- `common.function_initialize_state_log`;
- `common.function_upsert_current_state`;
- `common.function_protect_immutability`;
- `common.function_protect_revision_buffer_identity`;
- `common.function_validate_state_revision_entity`.

Триггеры документов обеспечивают инициализацию состояния, неизменяемость
реестров/ревизий/журнала, защиту идентичности буфера, временные метки,
согласованность ревизии и документа, синхронизацию кэша. Управляемых SQL VIEW нет.

## Запросы и операции

Лента и карточка используют Subquery для личного буфера, последней ревизии
и кэша. Чужие буферы исключаются до получения содержимого. Последняя ревизия
определяется по created_at DESC, id DESC. NULL из личного буфера сохраняет
приоритет для nullable-полей. Поиск выполняется PostgreSQL по актуальной
теме; удалённые документы исключаются, доступен фильтр стадии готовности.

Сервисы блокируют документ, затем буфер и состояние в согласованном порядке.
Фиксация сохраняет архивность/удалённость, создаёт draft-состояние и удаляет
буфер. Повтор текущего хеша возвращает существующую ревизию без новой записи.
Кэш и начальная запись состояния обслуживаются триггерами.

## Admin и API

Все маршруты ниже находятся под `/api/v1/`:

| Маршрут | Операции |
| --- | --- |
| `documents` | Создание, лента, карточка |
| `document-buffers` | CRUD только личных буферов; POST `{id}/commit/` |
| `document-revisions` | Чтение неизменяемых ревизий |
| `document-states` | Чтение и добавление состояния |
| `document-templates` | Создание и чтение реестра шаблонов |
| `document-template-revisions` | Создание и чтение версий шаблонов |

Обновление и удаление неизменяемых сущностей запрещены набором HTTP-методов.
Технические поля доступны только для чтения. Автор определяется запросом.
Используются проектные Session/TokenAuthentication, IsAuthenticated,
пагинация PageNumberPagination, DjangoFilterBackend, SearchFilter и OrderingFilter.
Ожидаемые нарушения целостности преобразуются в HTTP 400 без раскрытия SQL.
Общий доступ к документам соответствует messages; изоляция применяется к
личным рабочим буферам в API. Административный интерфейс, как и messages,
показывает буферы всех пользователей согласно административным правам.
Admin разрешает добавлять реестры, ревизии, шаблоны и записи журнала;
существующие записи неизменяемы. Кэш доступен только для просмотра. Буферы
можно создавать, редактировать, удалять и фиксировать выбранным действием.
При создании автор выбирается администратором, как в messages; после
создания идентичность буфера, хеш и временная метка защищены.

## Проверки и ограничения

Проверки выполнялись с Django 6.0.5, Python 3.14 и PostgreSQL 17 в отдельном
временном контейнере без рабочих томов. requirements.txt не менялся;
его требование Django >=6.1.1 в этом окружении не проверено.
Инструмент получения SDK PyCharm недоступен; использовано изолированное
окружение `/tmp/documents-check-env` с установленными зависимостями проекта.

Успешно проверены: Django check, отсутствие новых миграций, showmigrations,
sqlmigrate, чистая установка всех приложений, откат SQL-миграций до состояния
созданных таблиц и повторная установка при существующей структуре messages/documents.
Рабочая база не использовалась, fake/fake-initial не применялись.

Произвольная схема documents, ранее вручную созданная из SQL без истории
миграций, автоматически не принимается: перед её подключением необходима
сверка каталогов PostgreSQL и django_migrations. Обычная миграция намеренно
не скрывает конфликты уже существующих таблиц.

Полный набор тестов запускается из `application/codebase` командой
`python manage.py test`. Интеграционные тесты требуют PostgreSQL с pg_uuidv7
и pg_trgm и права создания тестовой базы. Результат финального запуска
зафиксирован в итоговом отчёте задачи.

Финальный результат: 20 тестов пройдено (PostgreSQL), Django check без ошибок,
makemigrations --check --dry-run: No changes detected; все миграции применены.
SQL стандартной миграции и триггеров сформирован командой sqlmigrate.

Права Admin сверены с messages: добавление реестров, ревизий и журнала,
просмотр кэша, редактирование и фиксация буферов. Проверены создание
документа через административную форму и действие фиксации выбранных буферов.
