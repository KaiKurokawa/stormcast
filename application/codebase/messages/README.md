# Приложение сообщений

Модели сохраняют структуру схемы `messages` из `messages.sql`. Все поля авторов ссылаются на стандартную модель пользователя Django через `AUTH_USER_MODEL`. Миграция приложения зависит от миграции модели пользователя, поэтому таблица авторизации создается раньше таблиц сообщений.

Первая миграция создает схему, типы, таблицы, ограничения и индексы. Последующие миграции устанавливают общие функции и триггеры приложения и обновляют проверку согласованности ревизий. Для базы, где таблицы уже созданы SQL-сценарием, первую миграцию нужно отметить выполненной с `--fake-initial`.

API расположен под `/api/v1/`:

- `messages/` — список и карточка сообщений, создание записи сообщения;
- `buffers/` — чтение, создание, изменение и удаление личных буферов; действие `POST buffers/{id}/commit/` создает ревизию и запись состояния в одной транзакции;
- `revisions/` — чтение неизменяемых ревизий;
- `states/` — чтение журнала и добавление нового состояния.

В админке можно создать ревизию для существующего сообщения; после создания её нельзя изменять или удалять. Выбранные буферы фиксируются действием «Зафиксировать выбранные буферы». Журнал состояний доступен для добавления, но не для изменения и удаления.

Ревизии и журнал состояний не поддерживают изменение и удаление. Текущий кэш состояния доступен только для чтения и обновляется триггером.

Для API нужен аутентифицированный пользователь Django. В тестовой конфигурации используется встроенная модель `auth.User` с целочисленным первичным ключом.
